# Agent 记忆基础与核心机制

Agent 的记忆问题不是“如何存下更多文本”，而是：哪些信息值得保存，什么时候应重新进入模型输入，冲突信息如何更新，以及如何验证模型使用了正确的信息。本篇建立通用概念；具体产品机制见 [Letta 记忆机制分析与洞察](Letta%20记忆机制分析与洞察.md)。产品实现与建议必须区分，不能从某一个实现推导所有 Agent 的行为。

## 1. 从一个跨会话任务理解记忆

假设一个开发助手负责 Atlas 项目。最初使用 SQLite，后来明确改用 PostgreSQL，并说明迁移原因；调试期间产生大量日志，订单表迁移仍未完成。过几天，用户新开会话要求继续工作。

助手需要辨别四种信息：当前事实是 PostgreSQL；SQLite 是历史选择；迁移原因可以回查；订单表迁移是未完成任务。把所有内容压成“正在开发数据库功能”，会丢失决定；把旧、新选择同时当作当前事实，又会产生矛盾。

持久化只解决信息存在的问题。完整链路是：

```text
对话或工具观察
→ 判断哪些信息值得保存
→ 提取、更新和持久化
→ 根据当前问题选择信息
→ 注入模型输入
→ 模型正确使用
```

其中任一步都可能失败。一个回答错误不一定是模型推理差，也可能是没有写入、检索漏掉、上下文组装遗漏或旧事实没有失效。

## 2. 分清五种状态

| 状态 | 主要保存什么 | 是否自动被当前模型看到 |
| --- | --- | --- |
| 原始事件或消息历史 | 用户消息、模型输出、工具调用与结果 | 不一定，需要加载或检索 |
| 当前上下文 | 当前请求实际提供的消息、指令与工具定义 | 是，但可见不等于正确使用 |
| 会话摘要 | 被移出上下文的历史的有损概括 | 被组装进请求后可见 |
| 持久记忆 | 精炼的事实、偏好、经验、规则和索引 | 取决于自动加载还是按需读取 |
| 外部知识或工作文件 | 代码、文档、数据等外部事实来源 | 需要读取或检索 |

核心记忆可以是持久记忆中每次都加载的部分；外部记忆可以是按需读取的部分。它们是运行时对信息的组织方式，不等于模型权重发生更新。Letta 的 MemFS 是这种组织方式的一个实例。[L03](参考资料.md#l03)、[L05](参考资料.md#l05)

“清空上下文”“新建会话”“重启进程”“删除记忆”也不是同一操作。新会话可能继承同一 Agent 的持久记忆；重启后可以从磁盘恢复；移出窗口的消息可能仍留在日志；删除当前文件后，版本历史还可能存在旧内容。必须依据具体实现判断每种操作影响哪些状态。

## 3. 写入：从观察到可靠的记忆

写入有两类触发：模型判断某件事值得保存，或者代码因用户命令、步骤数量、特定事件启动整理。代码触发了整理，不意味着代码能判断整理内容是否正确。

有用的记忆应区分事实、偏好、规则、推断与短暂任务状态。以下是一个设计示例，并非某产品的固定字段：

```json
{
  "subject": "Atlas.database",
  "value": "PostgreSQL",
  "status": "current",
  "supersedes": "SQLite",
  "source": "conversation/message-reference",
  "scope": "project:Atlas"
}
```

保留来源、作用域和替代关系，有助于解释为什么应使用新事实，而不是按文本相似度把旧事实再次选中。结构化字段本身不能证明内容为真，但可以使核验和更新更明确。

写入还需要处理：重复请求是否重复记忆；并发修改会不会覆盖；写文件成功而提交失败时状态是什么；何时算已保存；失败是否推进处理检查点。Git、数据库事务、版本号和幂等键各自提供不同保证，不能只因为“有版本管理”就宣称拥有完整事务语义。Letta 的提交失败与反思整合路径体现了这种区别。[L06](参考资料.md#l06)、[L07](参考资料.md#l07)、[L09](参考资料.md#l09)

## 4. 读取：常驻、按需检索与回查原文

常驻信息减少一次检索决策，却一直占用上下文，且错误、过时的信息也会被持续加载。按需读取节约常驻空间，但要经过“决定搜索—构造查询—选中结果—读取正文”的链路。

对 Atlas，短核心记忆可以写“当前 PostgreSQL；迁移原因见某文件”。详细说明保存在外部记忆，完整历史保留事实来源。这形成分层发现路径。目录名、描述和链接是检索设计的一部分，不只是文件组织风格。

文本检索擅长精确名称、错误码和文件路径，但容易漏掉同义表达；向量检索能提高语义匹配机会，却可能把相似但不属于同一项目、不同时间状态的事实混在一起。混合检索也需要作用域过滤、时效判断与结果核验，不能仅凭“用了向量库”宣称召回更准确。当前 Letta 本地历史检索的具体限制见产品分析。[L10](参考资料.md#l10)

查询“现在用什么数据库”和“最初为什么使用 SQLite”需要不同答案。检索后展开前后消息，可以检查后续更正，而不是只依据一个孤立命中结果。

## 5. 压缩：管理窗口，不等于长期学习

上下文压缩通常把较早消息换成摘要，并保留近期消息；长期记忆整理则从经历中提炼以后有用的事实和规则。两者可以由同一事件触发，但不应混为一个过程。

压缩的控制面包括触发阈值、切分边界、输入裁剪、输出长度限制与状态替换；摘要内容仍由模型生成。提示词可以要求保留关键约束和标识符，但不等于有程序逐项验证它们仍然存在。摘要的摘要会积累误差，原始历史与可追溯线索是补救路径。[L11](参考资料.md#l11)

请求前与响应后检查不冗余：上次模型响应以后，工具结果、用户附件、工具定义和记忆可能改变。请求前检查评估即将发送的输入；响应后检查纳入新增输出，并可以利用服务返回的 usage。两者均不能完全替代服务报溢出后的有界恢复。[L12](参考资料.md#l12)

## 6. 核心记忆与前缀缓存的取舍

提示词文本缓存和模型 KV／前缀缓存是两件事。前者减少应用重复拼装文本；后者减少模型处理相同输入前缀的计算。改变靠前的核心记忆，可能使后面虽然文字未变的历史失去缓存复用条件，因为其前缀已经改变。[G01](参考资料.md#g01)

```text
原请求：固定指令 → 记忆旧版 → 历史 → 问题
新请求：固定指令 → 记忆新版 → 历史 → 新问题
```

变化前的前缀可能仍可复用，具体取决于模型服务、缓存边界、有效期及请求设置。减少频繁修改、维持稳定前缀、把详细资料按需追加是可考虑的设计；把新规则作为会话后部的高优先级更新则依赖服务支持，不能向任意 API 随意添加 `role: system`。Letta 的特定模型分支见产品分析。[L14](参考资料.md#l14)

缓存命中也不会让输入不占上下文窗口。它优化重复计算和计费，不会自动增加模型可处理的上下文长度。

## 7. 用什么指标检验效果

以下是评估设计，不是任何产品的已公布成绩。

| 指标 | 定义 | 主要定位的问题 |
| --- | --- | --- |
| 写入覆盖率 | 应保存的关键事实中实际正确保存的比例 | 抽取和更新是否漏掉重要事实 |
| Recall@k | 标注相关记忆中被前 k 个检索结果找回的比例 | 检索漏召回 |
| Precision@k | 前 k 个返回结果中真正相关的比例 | 引入无关或错误作用域内容 |
| 注入覆盖率 | 关键事实中实际进入最终模型输入的比例 | 检索后筛选或组装遗漏 |
| 回答正确率 | 问题中符合当前事实与预期依据的答案比例 | 端到端效果 |
| 旧事实误用率 | 已更正事实被再次当作当前事实使用的频率 | 时效与冲突处理 |
| 压缩保真度 | 压缩后关键约束、决定、标识符、未完成事项的保留表现 | 摘要损失 |
| 成本与延迟 | 输入输出 token、整理调用、检索次数和耗时 | 工程可用性 |

核心记忆不经过 top-k 检索时，不应硬套 Recall@k；更应检查注入与使用。小样本多次复现可以定位故障，但不足以宣称总体召回率保证。

评估可使用固定的合成会话，预先标注应保存事实、历史事实和答案。比较截断、摘要、长期记忆、摘要加记忆四种策略，保持模型、问题、预算和数据相同；分别测试直接询问、同义表达、事实更正、跨会话、重启、连续压缩与跨项目混淆。没有运行真实模型时，只能验证状态流转，不能据此报告语义质量或实际调用成本。

## 8. Prompt 与代码应怎样分工

Prompt 适合表达判断原则、写作目标与检索策略；代码适合承担触发、权限、结构校验、持久化和有界重试。二者需要互补。

例如“不要在 Atlas 中继续使用 SQLite”写入记忆，有助于模型选择；如果发布物绝不能再包含旧配置，还应加入确定性配置检查。记忆应帮助判断，关键执行条件则由明确规则检验。把这些责任分开，才能判断系统到底保证了什么，以及哪里需要评估和补强。
