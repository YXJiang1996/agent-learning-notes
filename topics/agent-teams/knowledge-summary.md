# Claude Code Agent Teams：本轮知识点总结

整理日期：2026-09-12。范围：本轮对话已讨论的机制，不含尚未开展的源码课、论文全文研读或独立实现。

## 阅读方法与证据边界

- **官方说明**：产品公开行为，不等于取得了内部源码；页面会更新。
- **本机观察**：Claude Code 2.1.198、in-process、单队友实验，见[完整报告](../../experiments/claude-teams-2.1.198/report.md)。实验由助手操作。
- **设计建议**：用于自己实现或组织协作，不冒充 Claude Code 内部算法。
- **未验证**：没有足够证据，不能把“未公开”写成“绝对不存在”。

## 1. 团队、任务、上下文是不同对象

学习时分别考虑负责人、队友执行实例、任务记录、消息和代码产物。实例拥有自己的上下文；任务记录负责表达工作归属和状态。两次模型调用不一定构成两个可协作的 Agent，逻辑执行实例也不必对应两个操作系统进程。

本机配置里负责人和 observer 都记录为 in-process。任务创建、owner 设置、队友启动是不同调用：设置一个 owner 字符串本身不会创建执行者。[实测调用链](../../experiments/claude-teams-2.1.198/tool-events.json)

## 2. 创建与启动：一次观察不是唯一流程

本机实际顺序是：

```text
TaskCreate(#1)
→ TaskUpdate(owner=observer)
→ Agent(name=observer)
→ observer 读取 brief.md
→ SendMessage(main)
→ TaskUpdate(completed)
→ 负责人 TaskGet
```

这证明一次运行可以先建任务、再启动队友；不证明必须先创建全部任务再创建全部队友。已有队友也可以承接后续工作。

官方文档区分 v2.1.178 前后的设置流程：旧版 TeamCreate/TeamDelete 教程不能直接套用新版。[版本说明](https://code.claude.com/docs/en/agent-teams)

## 3. 存储文件：什么时候存在

本机曾观察到以下结构，`<团队>` 是占位符，不是字面目录名：

```text
~/.claude/teams/<团队>/config.json
~/.claude/teams/<团队>/inboxes/observer.json
~/.claude/teams/<团队>/inboxes/team-lead.json
~/.claude/tasks/<团队>/.lock
~/.claude/tasks/<团队>/.highwatermark
~/.claude/tasks/<团队>/2.json
```

退出后，团队目录已消失，任务目录和 pending 探针 2.json 仍在。因此退出后找不到 teams 文件，不与运行时观察矛盾。以点开头的文件和目录可能被文件管理器隐藏。

采样时邮箱都是空列表；任务 #1 的 completed 由 TaskGet 证实，但其 JSON 未被采到。不能因此推断完整邮箱消费算法或完成任务的保留策略。[状态快照](../../experiments/claude-teams-2.1.198/observed-state.json)

## 4. 分配、匹配与领取

官方支持负责人分配，也描述了队友完成工作后自领未分配且未阻塞任务的方式。[分配与领取](https://code.claude.com/docs/en/agent-teams#assign-and-claim-tasks)

设计上，“适合谁”要由任务要求、角色背景和分配策略表达。名字叫 backend 不会自动成为权限边界；提示词里的职责也不能代替工具限制。

需要分别判断：任务是否有 owner、依赖是否满足、执行者是否存在且能工作。不要把这些条件压缩成“任务已经写进表里，所以必然开始”。

## 5. 文件锁与所有权的边界

官方说明领取任务使用文件锁防止竞争；本机观察到 .lock，但没有测试竞争或追踪锁源码。[官方说明](https://code.claude.com/docs/en/agent-teams#assign-and-claim-tasks)

通用并发模型：读取可领取条件和写入 owner 必须处于同一原子操作中。Java 锁或数据库事务可以实现这类约束，但不是本次对 Claude 内部存储的结论。

必须区别：

- 防止两个执行者同时领取同一任务。
- 是否允许负责人重新分配已拥有的任务。
- 是否允许任意队友覆盖 owner。
- 是否保护多个任务共同修改的代码文件。

第一项的锁不能自动证明后三项的规则。此前“已分配任务不允许修改”的回答应限定为期望策略，不能写成已验证的硬性权限。

## 6. 依赖：解除阻塞不等于开始执行

本机任务 JSON 字段是 `blocks`、`blockedBy`，不是教学模型里的 `dependsOn`。本次没有设置依赖实验。

官方说明前置完成会自动解除依赖阻塞。[依赖管理](https://code.claude.com/docs/en/agent-teams#architecture)

例如任务 4 同时依赖 2、3：只完成 2，任务 4 仍不能开始；全部前置完成才具备依赖条件。没有证据保证“解除阻塞会自动唤醒已空闲的指定成员 B”。依赖状态、通知、执行是三个步骤。

建议明确约定交接：A 完成 3 并更新状态 → A 或负责人通知 B → B 查看 4 的最新归属、依赖和产物 → 开始执行。这是协作约定，不是默认固定调度算法。

## 7. 消息、状态与产物分别承载什么

| 信息 | 建议承载位置 |
| --- | --- |
| 谁负责、是否完成、依赖关系 | 任务记录 |
| 代码、接口约定、研究报告 | 可定位的文件或产物 |
| 结果交接、请求澄清、影响别人的发现 | 发给相关成员的消息 |

示例消息：“任务 3 已完成；接口实现位于 src/auth/login.ts；失败返回统一错误码。请核对任务 4 的状态后继续。”这是内容示例，不是固定工具参数。

本机 SendMessage 返回“排入主会话下一轮”，之后另一次 TaskUpdate 更新完成状态。这些独立调用没有证明事务、恰好一次投递或读取确认。消息发送成功也不能推导成接收方已经处理完毕。

推荐先确认产物并更新状态，再通知下游；接收方仍读取当前任务状态，避免只根据旧消息行动。实测中消息先于 completed，保留原始顺序，不为符合推荐流程改写历史。

## 8. 任务完成、队友空闲和关闭

任务 completed 是工作记录；idle 表示当前轮次停下；关闭表示执行者会话结束。三者不互相等价。

同一队友可以完成一项任务后继续另一项，也可能因等待条件而空闲。负责人不能仅凭所有队友空闲，就认定全部交付完成。

官方描述关闭请求可以被同意或附理由拒绝。[关闭队友](https://code.claude.com/docs/en/agent-teams#shut-down-teammates) 本机只做过退出主会话并停止后台工作，没有测试优雅关闭请求。任务文件留存也不证明旧执行者能够恢复。

## 9. 完成标准与 Hook 验收

“代码写好”“测试通过”“整体满足用户要求”是不同完成标准。任务应提前写明可检查的产物、验证条件和交接信息。

Claude 提供 `TaskCompleted` 与 `TeammateIdle` Hook，分别用于完成任务前和进入空闲前检查；命令 Hook 返回退出码 2 可阻止相应动作并反馈。[Hook 机制](https://code.claude.com/docs/en/hooks)

设计示例：完成测试任务前检查测试结果。不宜使用“团队还有任务，就禁止所有队友空闲”这样的规则，因为队友可能在合法等待依赖。Hook 提供检查入口，验收规则仍需自行定义。

建议收尾：收集结果 → 核对任务与产物 → 整体验证 → 必要时修正 → 关闭队友 → 汇报。各模块的局部验证不能替代接口联调。

## 10. 失败检测与恢复：重点未决问题

用户提出：队友挂掉，任务一直是 in_progress，负责人怎么知道？任务状态本身不能证明执行者还活着。

官方明确描述因 API 错误结束一轮时向负责人报告错误。[失败通知](https://code.claude.com/docs/en/agent-teams#context-and-communication) 这不等于证明所有进程崩溃或卡死都有可靠通知，也没有证明自动回收和安全重试整项任务。

下表是我们讨论的通用设计，不是 Claude 源码事实：

| 信号 | 能帮助判断什么 | 局限 |
| --- | --- | --- |
| 运行时捕获错误 | 本轮已失败 | 运行时自身突然消失可能无法报告 |
| 外部观察进程退出 | 对应进程已终止 | 进程存活不表示任务有进展 |
| 心跳 | 执行环境最近仍能响应 | 心跳正常也可能卡在业务逻辑 |
| 进度时间与超时 | 工作可能停滞 | 等待授权或长命令也可能超时 |

故障检测应由运行时或外部监控产生信号，再交给负责人决策；不能假定模型自己在后台持续监视系统。

建议恢复流程：发现疑似失效 → 核实状态 → 停止旧执行者或撤销提交资格 → 检查部分产物与外部副作用 → 重新分配。执行批次编号可以拒绝迟到结果，但如果旧执行者仍能直接写共享文件，它不能保护文件写入。重复外部操作还需要幂等处理。

## 11. 文件隔离与权限边界

本轮共享工作目录场景下，上下文独立不意味着代码隔离。任务锁保护领取过程，不保护任意源文件。分工约定、工具权限、工作目录隔离分别解决不同问题。

具体 worktree 配置、工具白名单、合并方式尚未深入学习；不把概念提及记成完成实践。

## 12. 已纠正的认识与后续问题

| 不准确的泛化 | 本轮采用的表述 |
| --- | --- |
| Agent 必须是独立 OS 进程 | 先区分逻辑执行实例和后端模式 |
| 指定名字就能限制角色能力 | 名称、职责约定、权限约束分开 |
| owner 更新会启动队友 | 分配与启动分别观察 |
| 有锁就不能修改已分配任务 | 竞争领取、重新分配与权限是不同问题 |
| 解锁任务就自动唤醒 B | 仅确认依赖解除；自动唤醒链路未验证 |
| 发出完成消息等于任务完成 | 消息、状态、验收分别处理 |
| 空闲就是已完成或已关闭 | 分别看工作状态与执行者生命周期 |
| 超时证明队友死亡 | 超时只形成疑似失效信号 |
| Claude 已有心跳、租约和自动恢复 | 尚未获得这类完整证据 |

下一步按用户偏好继续讲解上下文构造、Agent 执行循环、角色与权限；之后再做固定提交的开源 TS 对照。测试与故障实验暂缓，不要求先通过测验才能继续。
