# 产品、源码与论文研究

## 证据链

每个影响设计判断的结论应关联来源，并区分以下类型：

| 类型 | 最少记录 |
| --- | --- |
| 产品公开说明 | 官方页面、相关段落、访问日期、适用版本（已知时） |
| 源码事实 | 仓库 URL、提交 SHA、文件路径、关键符号及必要行号 |
| 运行观察 | 环境、命令或步骤、输入、输出、版本和日期 |
| 论文结论 | 题名、作者或标识、版本、章节及实验条件 |
| 推断 | 已知依据、推导过程、尚缺的验证 |

明确主张与出处的关系；不能只在文末堆链接。引用代码时优先给固定提交的链接，移动的默认分支链接不作为唯一版本依据。

## 读源码

先记录研究问题、版本和范围，再从与问题相关的执行入口追踪：入口 → 核心状态或数据结构 → 调度或调用 → I/O 边界 → 失败、取消和退出 → 测试与运行验证。

记录关键符号、调用关系及观察不到的动态调用。存在 CodeGraph 索引时遵循入口中的优先规则；工具不可用时披露限制，使用可用检索继续。不主动为第三方仓库建立索引。

README、注释和测试可以帮助定位意图，但不能单独证明实际路径已执行。构建或运行前审阅相关脚本及环境依赖，使用可复现的小范围输入；不要因为项目自称沙箱就假设运行任意代码安全。

源码分析保存到 `systems/<系统标识>/`；主题比较引用这些分析，不复制一整份。仅更新本次研究涉及的版本结论，保留旧版本依据。

## 比较方案

先给共同的使用场景与约束，再比较机制、接口与状态、并发和一致性、失败处理、扩展方式、延迟或成本、隔离边界、验证难度。只选择与问题有关的维度。

数据不足的格子写“未验证”或“未公开”，不要评分制造精确感。设计建议是针对约束的判断，不给脱离场景的统一排名。

主题问题示例：
- 多 Agent 协作：任务归属、通信协议、共享与私有状态、重试幂等性、取消和汇总。
- 记忆：写入触发、存储单位、检索和上下文注入、更新与遗忘、冲突及效果评估。
- 沙箱：威胁模型、进程与文件隔离、网络和权限、资源限制、生命周期与回收。

## 读论文

明确论文解决什么问题、方法的必要前提、基线和指标、结论适用条件以及没有证明的内容。只读到摘要时说明这一点，不声称核实了全文实验。

将方法连接到工程模块：输入输出、状态、检索或调度策略、实现成本和测试办法。代码看起来相似不代表项目采用该论文；没有作者、文档或代码出处证据时标为类比。

使用 `assets/paper.md` 记录。优先复现与当前问题直接相关的一小部分；不可复现时给出原因和可行的替代验证。
