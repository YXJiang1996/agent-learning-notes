# 研究型学习规划

## 目标和范围

将“大主题”转成一个可验证的工程目标。例如：“为一个支持并行任务的 Agent 系统设计消息与状态协议，并实现失败重试的最小实验”。

需要时了解现有语言与系统基础、目标用途、每周时间和目标深度。深度采用：了解机制、读懂源码、独立实现、面向实际场景设计。不要默认所有主题都要达到最高级。

按目标拆工程问题、前置基础和可选拓展。前置关系必须有具体理由，无需把所有相关学科列为必修。已有基础可以用少量诊断问题核实，允许用户跳过。

## 研究对象选择

尊重用户指定的产品、仓库和论文。没有指定时，核实候选的实际适配性：是否覆盖目标机制、能否获得实现证据、可复现性、复杂度、维护与版本情况。热度或 star 数不能单独证明成熟。

优先选择一个主项目深入研究，再按设计差异选择一至两个对照项目；对照数量按问题调整。闭源产品适合研究公开能力与行为边界，不承担源码事实的角色。

## 计划产出

使用 `assets/plan.md`，以任务和验收条件组织阶段：

1. 问题定义：使用场景、约束、目标深度与不在本轮范围的事项。
2. 必要基础：针对源码或设计问题补学，不要求先学完整理论体系。
3. 实现分析：主项目代码路径、关键数据结构、失败路径。
4. 方案与论文：相同问题下的差异、方法条件及证据。
5. 最小实验：正常路径、失败或边界案例及观察指标。
6. 解释与迁移：学习者自己的方案、取舍和可复现验证。

给出任务的预计工作量范围和可执行的下一步。时间预算未知时不排具体日期。论文与实验可穿插进行，不强制流水线式完成。

## 调整

任务状态为未开始、进行中、已完成或暂缓，与掌握维度独立。根据测评错误或实现阻碍调整后续任务：补齐直接缺口，减少重复阅读，保留调整原因和已完成任务。依赖缺口会影响后续设计时明确标出，但用户选择探索后续内容时不要强制阻止。
